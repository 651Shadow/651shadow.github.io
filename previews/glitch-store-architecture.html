1. Preventing Argon2id CPU Exhaustion via O(1) Indexed Lookup

Pre-audit flaw (F-03 / AUDIT-004): API keys share a static gstore_ prefix. Earlier queries filtered user_api_keys by key_prefix and looped over returned candidate rows running argon2id verification on each row. An attacker could force repeated expensive password-hash evaluations per HTTP request.

Implemented fix (src/lib/api-keys/lookup.ts + migration 0035_api_key_lookup_hash.sql): Incoming headers are capped at 64 bytes via capKeyInput() before any hashing. We compute an indexed HMAC-SHA256 prehash keyed by server secret KEY_LOOKUP_PEPPER, fetch at most one row by equality on key_lookup_hash, and run argon2id verification once against the stored key_hash. Plaintext keys are never persisted. 

// src/lib/api-keys/lookup.ts + src/app/api/secure-proxy/route.ts
const cappedKey = capKeyInput(apiKey); // rejects keys > 64 bytes
const lookupHash = computeKeyLookupHash(cappedKey); // HMAC-SHA256(key, KEY_LOOKUP_PEPPER)

const { data: candidate } = await admin
  .from("user_api_keys")
  .select("id,user_id,key_hash,salt")
  .eq("key_lookup_hash", lookupHash);

// argon2id remains the single cryptographic source of truth on the indexed row
Security note: HMAC lookup prevents attackers from forcing O(N) KDF scans and reveals nothing without the server pepper, while Argon2id still enforces slow-hash verification on the matched key row. Legacy rows without key_lookup_hash use a tight fallback cap until rotated.

2. Multi-Layer SSRF & DNS-Rebinding Guard (Node Proxy + Neutralized Edge Mirror)

Pre-audit flaw (F-04 / C1 & AUDIT-003): Both the Next.js route and an older Deno Edge Function (supabase/functions/secure-proxy/index.ts) could forward traffic to arbitrary upstream base_url targets or follow 3xx redirects without validating resolved IPs.

Implemented fix (src/lib/local-apis/upstream-proxy.ts): First, buildForwardUrl() performs up to 8 decoding passes to reject obfuscated traversal (%2e, .., backslashes, control chars). Next, validateUpstreamUrlBeforeFetch() rejects non-HTTP(S) schemes, embedded URL credentials, localhost / .local, cloud metadata hosts (169.254.169.254, metadata.google.internal), enforces ALLOWED_UPSTREAM_HOSTS when configured, and runs dns.promises.lookup(hostname, { all: true }) checking every IPv4/IPv6 record against private, loopback, link-local, CGNAT (100.64.0.0/10), IPv4-mapped IPv6 (::ffff:), and NAT64 blocks. Finally, fetch() uses redirect: "manual" and rejects 3xx or unexpected HTTP 200 HTML error pages with 502. The redundant Deno edge proxy was fail-closed with 503.

Residual TOCTOU trade-off: Calling dns.lookup() right before standard fetch() stops static internal DNS records, but a zero-TTL rebinding record could theoretically rotate between lookup and socket connect unless ALLOWED_UPSTREAM_HOSTS allowlisting is active or the resolved IP is pinned inside a custom HTTP dispatcher/agent.

3. Upstream Secret Encryption at Rest (AES-256-GCM)

Implemented in src/lib/crypto.ts (F-05 remediation): Third-party provider keys stored in apis.admin_api_key_encrypted are encrypted server-side using Node aes-256-gcm with a 32-byte key derived from ADMIN_KEY_ENCRYPTION_KEY, a fresh 12-byte random IV per write, and a 16-byte authentication tag. Column-level public read privileges on encrypted credential columns and internal base_url fields are revoked from anon and authenticated Postgres roles.

4. Atomic Credit Deduction & Non-Negative Balance Invariants

Pre-audit flaw (F-06 / AUDIT-001): Trigger handle_credits_ledger_insert() lacked a >= 0 guard, and concurrent API bursts could drive users.credits_balance negative.

Implemented fix (supabase/migrations/0034_atomic_deduct_credits.sql): Added NOT NULL and CHECK (credits_balance >= 0) on public.users, raised SQLSTATE 23514 in the ledger trigger on underflow, and introduced the conditional Postgres RPC below. On deductError, secure-proxy returns 402 Payment Required. 

-- supabase/migrations/0034_atomic_deduct_credits.sql (SECURITY DEFINER, service_role only)
update public.users
  set credits_balance = credits_balance - p_amount
where id = p_user_id
  and credits_balance >= p_amount
returning credits_balance into v_balance;
Concurrency note: Credits are checked pre-flight and atomically debited after a non-HTML 2xx response so users never pay for upstream failures. Under simultaneous burst race conditions against a low balance, Postgres prevents negative balances cleanly; full elimination of one extra upstream forward before 402 is a two-phase pre-hold extension.
